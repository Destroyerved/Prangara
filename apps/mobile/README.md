# PRANGARA mobile (Android APK)

The web dashboard, on a phone. Every module the browser app has — footprint,
leak points, what-if simulator, circular actions, abatement portfolio with the
MACC, marketplace and RFQs, green logistics, circular network, compliance
readiness and methodology — plus the things only a phone can do: camera intake
of bills and nameplates, conversational onboarding, evidence capture, and a
queue that drains when the signal comes back.

It shares the web app's design system value for value: the monochrome dark
theme with a near-black `#060708` ground and a white accent on glass surfaces,
colour reserved for data (scopes `#fb923c / #818cf8 / #38bdf8`, cash-positive
`#10b981`, net-cost `#f43f5e`), and the same Manrope/Inter type ramp with its
tight display tracking. `src/theme/tokens.ts` is a direct port of
`src/styles/tokens.css`.

## Running it

```bash
cd apps/mobile
npm install
npm start
```

Then press `a` for an Android emulator, or scan the QR code with Expo Go.

### Pointing it at the backend

The client resolves the API in this order:

1. a stored endpoint the user typed into the Account screen (persisted, so it
   survives a restart)
2. `EXPO_PUBLIC_API_URL`
3. the host serving the Expo dev bundle, on port 8000
4. the deployed API at `https://prangara.vercel.app`

Release builds bake `EXPO_PUBLIC_API_URL=https://prangara.vercel.app` in, so an
installed APK signs in over any network with no laptop in reach.

Step 3 is why a physical phone usually works with no configuration: the dev
server already knows the laptop's LAN address. If it does not, set it
explicitly — **`localhost` on a phone is the phone**:

```bash
EXPO_PUBLIC_API_URL=http://192.168.1.20:8000 npm start
```

Over a USB cable, `adb reverse` is simpler than any LAN address:

```bash
adb reverse tcp:8000 tcp:8000
```

The phone's `127.0.0.1:8000` then reaches the laptop's backend, and the Account
screen's endpoint switcher can be set to `http://127.0.0.1:8000`.

The Account screen shows which URL the app resolved and whether the API
answered, which is the first thing to check when a demo will not load.

### With no backend at all

The sign-in screen offers **Open the demonstration**. That runs the app against
`src/data/demo-assessments.json` — ten sectors of real engine output, generated
by `backend/engine` and regenerated by the snippet in
`docs/DEMO-FIXTURES.md` — so a freshly installed APK is fully explorable on a
factory floor with no server in reach. It is labelled as demonstration data on
every screen that shows it, and capture and procurement stay read-only, because
those write to a real plant's record.

## Reading a photograph on the phone

Text recognition and image labelling run **on the device**, with the models
bundled into the APK rather than downloaded, so a bill or a nameplate can be
read standing next to the machine with no signal and without the photograph
leaving the phone.

```text
src/ml/ocr.ts         ML Kit text recognition, with per-line geometry
src/ml/text.ts        rebuilds printed rows from that geometry
src/ml/documents.ts   bill and invoice field rules
src/ml/nameplate.ts   equipment plate field rules
src/ml/vision.ts      ML Kit image labelling, to check the framing
```

The geometry step is what makes it work on real documents: a recogniser returns
a two-column nameplate as separate lines - "kW", "VOLTS", "RPM" in one block and
"7.5", "415", "1440" in another - so the rows are rebuilt from where the text
sits on the page before any rule runs. On a test plate that took the reading
from 4 fields to 11.

Every extracted value carries a confidence and the exact printed line it came
from, and nothing is written until a person confirms it. The rules refuse more
than they accept: a number with a leading zero is an identifier rather than a
quantity, an amount needs a currency token beside it, and an implausible figure
is dropped rather than shown. A tariff is read only where the bill prints a
rate - it is never back-calculated from the total, because a bill's total
carries fixed charges and duty and the result would be a plausible-looking lie.

The image labeller exists to catch the most common failure on a factory floor:
a mis-framed photograph. It is a hint, never a gate.

If a build is made without the native modules, the app says so on the Capture
tab and in Account, and falls back to the server extractor or manual entry.

## Building an APK

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build-apk.ps1
```

The script regenerates the native project when needed, restricts the build to
`armeabi-v7a,arm64-v8a` (x86 slices only ever load on an emulator and roughly
double the download), assembles the release variant, and copies the result to
the repository root as `prangara-companion-release.apk` with its size and
SHA-256. Pass `-Clean` to force a full `expo prebuild --clean` first.

`android/` is generated and git-ignored, which is why every build setting that
has to survive a regeneration lives in that script rather than in a file inside
it.

With an Expo account, `npx eas build --platform android --profile preview`
still works.

## Layout

```text
src/
  api/         client (auth refresh, typed errors, timeouts), endpoints, types
  auth/        session context, including the offline demonstration mode
  components/  UI primitives, page furniture, and the SVG charts
  data/        bundled engine demonstration payload and cluster reference content
  lib/         number formatting for an Indian industrial audience
  navigation/  five tabs plus every module as a pushed screen
  screens/     one file per screen
  storage/     tokens in the Android keystore, offline capture queue
  theme/       design tokens ported from the web app
  workspace/   the active plant and the assessment every module reads
```

## Rules this app follows

- **It never computes a carbon or financial number.** Every figure comes from
  the backend's deterministic engine, or from the bundled engine payload
  (PRD 3.1). The what-if simulator sends a named, closed-set modification to the
  server and reruns the real engine rather than approximating locally.
- **Extraction is never persistence.** Conversational onboarding and bill
  scanning show unconfirmed values with their confidence and the words they
  were read from; nothing is written until the user confirms (PRD 29).
- **It says which extractor ran.** When the backend has no language model or OCR
  runtime configured, the screen says so rather than implying a scan happened.
- **Missing is not zero.** A figure the engine did not supply reads
  "Unavailable" or "Not supplied", never `0`.
- **Status is never carried by colour alone** — every severity chip and data
  state also shows a word (PRD 30, accessibility). Charts carry an
  `accessibilityLabel`, because text inside an SVG reaches no screen reader.
- **Field names come from the contract.** `packages/contracts/openapi.json` is
  the source; `src/api/types.ts` mirrors it and invents nothing.

## Known limits

- The offline queue carries a `clientRef` the intake and evidence endpoints do
  not yet consume, so replay safety still rests on only retrying network
  failures.
- The *server* OCR runtime is still unconfigured, so "ask the server" reports
  that. On-device reading does not depend on it.
- The on-device models are bundled rather than fetched from Play Services,
  which is what makes them work offline and what takes the APK from 58 MB to
  96 MB. An unbundled build would be far smaller and would need a network on
  first use.
- The rules cover Indian utility bills, fuel and freight invoices, and motor,
  pump, compressor and boiler plates. An unfamiliar layout reads as "no figure
  matched" and falls back to manual entry rather than guessing.
- A data-quality score needs the stored profile and activity records, so the
  bundled demonstration payload has none and the modules say "Not supplied"
  rather than inventing one.
- The release variant is signed with the generated debug keystore, which is
  fine for sideloading and wrong for Play distribution.
